# Software Metrics

- **Definition**: A measure of measurable/countable software characteristics.  
- **Purpose**:  
  - Measure software performance  
  - Plan work items  
  - Assess productivity, size, cost, etc.  

## Types of Software Metrics  
1. **Product Metrics**  
2. **Process Metrics**  
3. **Project Metrics**

### 1. Product Metrics

- **Purpose**: Measure software product quality (performance, reliability, maintainability).  
- **Use Case**: Evaluate the software itself.  

##### Examples:  
- **Cyclomatic Complexity**: Code complexity measurement.  
- **Response Time**: System performance metric.  
- **Reliability Metrics**: Failure rate, bug count.  
- **Defect Density**: Defects per unit size of code.

### 2. Process Metrics

- **Purpose**: Measure efficiency and effectiveness of the development process.  
- **Use Case**: Process improvement and defect prevention.  

##### Examples:  
- **Defect Removal Efficiency (DRE)**: Tracks defect elimination before release.  
- **Mean Time to Failure (MTTF)**: Average operational time before failure.  
- **Review Efficiency**: Evaluates code review effectiveness.

### 3. Project Metrics

- **Purpose**: Measure project management factors (cost, schedule, productivity).  
- **Use Case**: Track progress and allocate resources.  

##### Examples:  
- **Cost Variance (CV)**: Difference between planned vs. actual cost.  
- **Schedule Variance (SV)**: Difference between planned vs. actual timeline.  
- **Effort Estimation**: Predicts effort required to complete the project.

## Size Metrics

Size metrics measure the size of software in terms of:

1. lines of code (LOC) **or**
2. functional units.

### Lines of Code (LOC)

- **Definition**: Counts total source code lines in a program.  
- **Uses**:  
  - Effort estimation  
  - Cost prediction  
  - Productivity analysis  

##### Example:  
| Project | LOC    | Developer Effort (Person-Months) |     |
| ------- | ------ | -------------------------------- | --- |
| A       | 10,000 | 4                                |     |
| B       | 25,000 | 10                               |     |

##### ✗ Limitations:  
- Does **not** measure code quality.  
- Language-dependent (same functionality may yield different LOC counts).

### Functional Point (FP) Analysis

- **Primary Purpose**:  
  Measures and communicates the **functional size** of a software application to clients/customers.  
- **Additional Uses**:  
  - Tracks software project **development** and **maintenance** consistently.  
  - Technology/tool-agnostic metric.

### Cost Estimation Models

- **Static Model**:  
  Uses a **single variable** as key for cost/time calculation.  
- **Dynamic Model**:  
  All variables are **interdependent** (no basic variable).  

#### Model Types:  
1. **Static, Single Variable Models**  
2. **Static, Multivariable Models**

#### Static Single Variable Model

**Purpose**: Estimates effort, cost, and development time for software projects based on a single variable (typically size).  

**Equations**:  
- **Cost (C)**:  
  $C = \alpha \times (\text{LOC})^b$
- **Effort (E)**:  
  $E = \alpha \times (\text{LOC})^b (Person-Months)$
- **Development Time (DT)**:  
  $DT = \alpha \times (\text{LOC})^b(Months)$

**Variable**:  
- **LOC**: Number of Lines of Code.

---
## Questions on Static models

#### Q.1 Question 1:

A software project has an estimated size of **12,000 LOC**. Given constants:  
- \( a = 1.8 \)  
- \( b = 1.15 \)  
Estimated cost of project?
## Solution:  
Using the cost formula:  
$\text{Cost} = a \times (\text{LOC})^b$  
$\text{Cost} = 1.8 \times (12,\!000)^{1.15}$ 
**Estimated Cost**: \$38,826.94

### COCOMO Model (Constructive Cost Estimation Model)

- **Purpose**:  
  Predicts **effort** and **schedule** for software development based on project size.  
- **Significance**:  
  One of the most widely used software estimation models globally.

#### COCOMO Model: Advantages & Disadvantages

##### **Advantages**  
✅ Leverages **historical data** for accurate estimates.  
✅ **Easy to implement** and understand.  
✅ Simplifies **total project cost** estimation.  
✅ **Drivers** clarify impact of various project factors.  

##### **Disadvantages**  
❌ Ignores **hardware issues** and **staff turnover**.  
❌ Overlooks **documentation** and **requirements**.  
❌ Over-reliant on **time factors**.  
❌ Limits **cost accuracy**.  
❌ Oversimplifies **security/safety** impacts.  
❌ Neglects **customer skills/cooperation**.

#### Basic COCOMO Model

**Purpose**: Estimates project parameters (effort, time, team size) based on software size.  

**Formulas**:  
- **Effort (E)**:  
  $E = a \times (\text{KLOC})^b (Person-Months, PM)$  
- **Time**:  
  $\text{Time} = c \times (\text{Effort})^d(Months)$  
- **Personnel Required**:  
  $\text{Personnel} = \frac{\text{Effort}}{\text{Time}}$  

**Variables**:  
- **KLOC**: Size in *Kilo Lines of Code*.  
- **a, b, c, d**: Constants (vary by software type).  
- **Effort**: Total development effort in *Person-Months*.  
- **Time**: Estimated development time in *Months*.
